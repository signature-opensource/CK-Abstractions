# CK.Abstractions

The contracts of the Real Objects, Poco and Auto Services features. Almost everything here is a marker
interface or an attribute carrying no logic of its own - what gives them meaning is the CKomposable
engine reading them. The exceptions are small and worth knowing: `ConfigurableAutoServiceKind` is a
`[Flags]` enum, `IAmbientServiceDefaultProvider<T>` declares a real `Default` member, and
`EngineAttribute` and `PreserveAssemblyReferenceAttribute` carry state and computed properties.

This is a very high-level overview. To grasp the whole picture, take a deep breadth: there's a lot to
process under the tip of the iceberg.

## Real Object

First come the Real Objects. Their goal is to represent actual object or concept of the real, external,
world: a database, a cloud subscription, a table in a database, a folder, a git repository: all these
beasts exist; they are "Real Object":

- They are true singletons.
- They are often immutable and expose pure functions (mutability and side-effect must be handled with
  care because of concurrency).
- A Real Object can depend from any number of other Real Objects without cycles: this is a classical
  [DAG](https://en.wikipedia.org/wiki/Directed_acyclic_graph), but ONLY other Real Objects appear in
  this graph.
- A Real Object can "refine"/"extend" a base one (simple inheritance).

So far so good. But doesn't this look like basic object programming?

Yes... with one major difference: these types are analyzed by the CKomposable engine and **one and only
one most specialized type must exist** for any object hierarchy. This applies to interfaces as well as
classes: a `public interface IUserTable : IRealObject` is necessarily, eventually, a singleton. Any
ambiguous implementation triggers an error.

RealObjects implementations are often *abstract class* with *abstract* methods: their final
implementations are generated by "Aspects", the CKomposable engine's plugins.

RealObjects are *de facto* singleton services (and are registered as such in the DI container) but they
can only depend on other RealObjects. They are used as backbones of the system: their dependency graph
is used to structure and organize features like code generation, database setup and migration, external
scripts execution, etc.

See [`IRealObject`](Core/AutoDI/IRealObject.cs) and the
[Automatic DI contracts](Core/AutoDI/README.md) for the details.

## Poco

Then come the Poco (Plain Old C# Objects) that are simple objects. Poco are typically used as
[Data Transfer Object](https://en.wikipedia.org/wiki/Data_transfer_object), they carry data and have no
or very few associated behaviors.

This Poco concept fulfills 2 goals:

- Supporting true modularity: any modules/packages can enrich any `IPoco` interface independently of
  others.
- Defining a "closed world" of DTO that are the only ones that should be authorized to be exchanged
  with external parties.

By allowing independent packages (packages that don't know each other) to simultaneously extend the
same *eventual* type, the [`IPoco`](Core/Poco) interface is one of the key of the *Package First*
approach.

The [Poco attributes](Core/Poco/Attributes) work at two levels. `[PrimaryPoco]`, `[SecondaryPoco]` and
`[AbstractPoco]` qualify an **interface**'s role in the composition. `[NotExchangeable]` and
`[NotSerializable]` restrict what may be done with a **type** - an IPoco interface, but also a record
struct or an enum. And `[NullInvalid]` and `[EmptyInvalid]` constrain a **property**'s value.

`[SealedPoco]` and `[VirtualPoco]` are declared but both carry the same remark: *"As of September 2025,
this is not yet supported."*

## Automatic DI

Last but not least, the Automatic Dependency Injection aims to relieve the developer of the burden of
DI configuration. Basically, by using the [`IAutoService`](Core/AutoDI/IAutoService.cs) marker
interface (along with [`ISingletonAutoService`](Core/AutoDI/ISingletonAutoService.cs) and
[`IScopedAutoService`](Core/AutoDI/IScopedAutoService.cs)), and the
[`IsMultiple`](Core/AutoDI/IsMultipleAttribute.cs) attribute, the DI container can be automatically
optimally configured (every service that CAN be singleton will be registered as singleton).

The full contract set is documented in [Core/AutoDI](Core/AutoDI/README.md).

## The three families of markers

| Folder | Applies to | Attributes |
|--------|-----------|------------|
| [Core](Core/README.md) | types, in the `CK.Core` namespace | `[CKTypeDefiner]`, `[CKTypeSuperDefiner]`, `[ExcludedCKType]`, `[AlsoRegisterType<T>]` |
| [Core/AutoDI](Core/AutoDI/README.md) | the DI contracts and their attributes | `[IsMultiple]`, `[ReplaceAutoService]`, `[ScopedService]`, `[SingletonService]`, … |
| [Setup](Setup/README.md) | **assemblies**, in the `CK.Setup` namespace, from `AssemblyInfo.cs` | `[IsPFeature]`, `[IsPFeatureDefiner]`, `[IsEngine]`, `[RequiredEngine]`, `[SkippedAssembly]`, `[RemovePFeature]`, `[RemoveType]`, `[AddType]`, `[PreserveAssemblyReference]` |

The distinction matters: the `Setup` attributes are declared in `AssemblyInfo.cs` rather than on a type.
Four of them decide what the engine looks at, and two of those work by contagion: `[SkippedAssembly]`
excludes, `[IsPFeature]` includes, `[IsPFeatureDefiner]` makes *"any assemblies that references it"* a
PFeature, and `[IsEngine]` marks an engine - *"Being an Engine is transitive"*. The rest do narrower
jobs: `[RequiredEngine]` names a required engine assembly and a NuGet version range,
`[PreserveAssemblyReference]` keeps a reference from being trimmed away, and `[AddType]` / `[RemoveType]`
act on individual types. Four are `AllowMultiple = true`, so "once per assembly" holds for the shape of
the file, not for the attribute count.

One rule is easy to miss and changes what you can do with these markers: **they are matched by name, not
by identity**, so a package can declare its own instead of referencing this one.

The attributes say it of themselves:

> This attribute [...] can be created anywhere: as long as the name is "CKTypeDefinerAttribute"
> (regardless of the namespace), it will be honored.

`IRealObject`, `IAutoService`, `IScopedAutoService` and `ISingletonAutoService` grant the same licence,
with one extra condition: *"any empty interface (no members) named `IAutoService` defined in any
namespace will be considered as a valid marker"*. A look-alike that declares a member is not one.

## Reaching the engine side

[`EngineAttribute`](Core/EngineAttributes/EngineAttribute.cs) and
[`ChildEngineAttribute<T>`](Core/EngineAttributes/ChildEngineAttribute%7BT%7D.cs) are **abstract base
classes**, not attributes you apply. You specialize them, and the base constructor takes one string:

> Assembly Qualified Name of the associated engine implementation that must be a specialized
> `CK.Engine.TypeCollector.EngineAttributeImpl` class

for example `"CK.TypeScript.Engine.TypeScriptPackageImpl, CK.TypeScript.Engine"`. So the attribute you
write lives in deployed code and *"can declare any properties that configures the behavior of its Engine
peer"*, while the class that acts on it lives in an engine assembly that is never deployed - and the
only thing linking them is that string. That is how an attribute defined here gets behaviour from a
package this one never references.

`ChildEngineAttribute<T>` extends an existing `EngineAttribute` rather than replacing it: *"An existing
`IEngineAttribute` of a type assignable to `T` is required and must appear before this one."* A root
attribute can be augmented by any number of children.
